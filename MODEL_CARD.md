# Model card: retail demand forecasting models

Three forecasting models, each built for one planning decision and evaluated on that decision. All numbers come from `results/*/` (generated by the code) and are reproduced in `reports/`.

## Part A: weekly ordering, 500 product × outlet series (TCS iON data)

| | |
|---|---|
| **Decision supported** | Weekly order-up-to stock per product and outlet, target fill rate 95% |
| **Models** | Point forecast: extra trees (200 trees, min_samples_leaf 20), daily units, 7 days ahead. Ordering: quantile gradient boosting (q = 0.9) of the next 7-day total, with one scale factor set on the 8 weeks before the test |
| **Inputs** | Sales up to the order date (levels over 7-112 days, same-weekday mean, volatility, zero share, days since last sale, sale size and interval, Croston / SBA / TSB estimates), product / department / outlet / state, the week's planned price relative to the item's usual price, calendar |
| **Training data** | 2012-01-01 to 2014-01-03 (weekly order dates from day 112) |
| **Validation** | 4 expanding-window folds of 8 weekly order dates; test period 2014-01-04 to 2014-02-28, used once |
| **Test performance** | Daily RMSE 3.317 vs 3.451 (TSB), 3.526 (SBA), 3.553 (28-day average); weekly-total WAPE 44% |
| **Decision performance** | 10.1% less stock than the per-item 90th-percentile rule at equal 95% fill (series bootstrap CI 6.0-16.7%); 41.8% less than the 28-day-average rule |
| **Explanation** | Exact TreeSHAP on the tuned Poisson gradient-boosting model (ties with extra trees on test RMSE): the TSB estimate dominates |
| **Known limits** | One 8-week winter test period; no stock-out records (zero sales may hide stock-outs); price effects weakly identified (prices change in about 1% of weeks); costs unknown, so compared at a fixed fill rate |

## Part B: store × family replenishment (Favorita)

| | |
|---|---|
| **Decision supported** | Stock per store and product family for the next 7- or 16-day order cycle |
| **Models** | Random forest on log1p(sales) (min_samples_leaf 10); Ridge regression on log1p(sales) as the robust alternative |
| **Inputs** | Sales up to the order date, same-weekday history, store transactions and oil price at the order date; planned promotions, holidays (national / regional / local, transfers), payday and calendar for the target day |
| **Validation** | 4 sixteen-day windows (May-July 2017); test window 31 Jul - 15 Aug 2017, used once |
| **Test performance** | WAPE 16.3% (random forest), 16.1% (Ridge), vs 20.7% for last week's sales; RMSLE 0.447 |
| **Decision performance** | No forecast reduced the stock needed for a 99% fill rate versus the 28-day-average rule (random forest +6.8% on 7-day cycles); documented as a negative result |
| **Known limits** | One test window, containing a holiday long weekend (random forest over-forecast it by about 22%); no prices or stock levels in the data |

## Part C: week-ahead hourly capacity plan

| | |
|---|---|
| **Decision supported** | Capacity (staff) for each hour of next week, with unmet demand costing 3× idle capacity |
| **Models** | Quantile gradient boosting at the 75th percentile (cost-optimal quantile); extra trees as the point forecast |
| **Inputs** | Only data at least one week old: hour-of-week profiles and lagged levels, calendar |
| **Validation** | Rolling-origin cross-validation; test period Jul 2020 - Feb 2021 (4,525 recorded hours), used once |
| **Test performance** | Point MAE 29.3 (WAPE 38.1%), not better than the static hour-of-week profile by more than noise; 80% intervals cover 78.9% |
| **Decision performance** | 6.9% lower cost than the best rule-of-thumb plan (CI 1.5-14.3%); 38.5% lower than seasonal naive plus buffer |
| **Known limits** | Undocumented source and unit; a 30-day recording outage is excluded; missing hours are not random (mostly quiet night hours) |

## Common to all parts

- Features use only information available at the forecast date; tests in `tests/` change the future and check that no feature moves.
- Hypotheses are tested with Holm correction; uncertainty is given as bootstrap intervals (series-, store- or block-bootstrap as appropriate).
- SHAP values come from my own exact TreeSHAP implementation, checked against the `shap` package in CI.
- Not suitable for: new products or outlets without history, periods with structural breaks (new stores, price policy changes), or automatic ordering without a human review of large orders.
